I got the idea for this while reading Martin Fowler's _Refactoring_. At one
point he references another book about software patterns (the Gang of Four's
_Design Patterns_, from 1994), and I was really surprised to see that the
command pattern was in there.

The command pattern is where you make a class instead of a function, so you can
decompose the function into its constituent parts, group them under that
class, and expose an `execute` method on it. So you have a complex function
that's essentially nicely abstracted, and you call it the same way you'd call
any function. Something like this, in Ruby:

```ruby
class ApproveLoanApplication
  def self.execute(application:)
    new(application).execute
  end

  def initialize(application)
    @application = application
  end

  def execute
    validate!
    offer = build_offer
    record_decision(offer)
    notify_merchant(offer)
    offer
  end

  private

  def validate!
    raise InvalidApplication unless @application.complete?
  end

  def build_offer
    # ...
  end

  def record_decision(offer)
    # ...
  end

  def notify_merchant(offer)
    # ...
  end
end

ApproveLoanApplication.execute(application: application)
```

Whoever calls it just sees the one method, and when you open the file the
`execute` method reads kind of like a table of contents for everything below
it.

We use this all the time at Stripe. I had no idea that this was a
general software pattern that went far beyond Stripe, let alone one with its own
chapter in a book from the nineties.

It really reminded me how many software patterns there are out there that I
might not know of, or that I do know of but never knew had a name, and that
form the core of my understanding of how to be a software developer anyways.

We tend to think of computer science or computer engineering as a settled
science, or a settled engineering field. But really it's quite unsettled
still, and I think that's what makes it really interesting. There are decades
of engineering thinking on problems where there's no correct solution, and
people have iterated on models that inform what we know. None of that was
self-evident to an engineer working before AI. Somebody had to notice it and
write it down.

Now that AI has totally recreated the way we write software through coding
agents, the entire field is sort of back open. A lot of the patterns we already
discovered are still useful for sure, and some of them are even more useful now
than they were. But there are also hundreds or thousands of new patterns for
how we'll write software that nobody has consolidated into best practices yet.

So I wanted to begin writing these down, both things I do at Stripe and things
I do outside of Stripe on my side project. Here's a first batch.

## 1. Do the giant refactor, then backfill coverage against main

You do a giant refactor and then you stop. You take the existing main branch
and your refactor branch, give them both to a coding agent, and say something
like:

> I want you to build 100% behavioral coverage of everything that I've
> refactored, but I want you to build that 100% line coverage against main.
> Think about every possible way that this refactor could fail and make sure we
> have total coverage.

Then you check that those tests pass on main, and see whether or not they fail
on your new branch. If something passes on main and fails on your branch, you
changed behavior somewhere, and now you know where.

You might think this is kind of useless, because the agent has access to
everything. It can read the refactor it's supposed to be catching, so there's
no test holdout. But in practice I've found it extremely helpful. I think it
works because the tests have to pass on main first, so they end up describing
how the old code behaved and not how the agent thinks the new code should
behave. This is one of the core things that has let me do gigantic refactors,
like 50,000-line refactors, that I don't think I'd have had the nerve to merge
otherwise.

## 2. PR walkthrough videos

This one is basically a prompt in `AGENTS.md` that tells the agent to always do
a full end-to-end manual test of whatever it built and record a video of it,
and then to add voice narration where the agent explains the walkthrough.

This sounds totally crazy, but it has become one of the most turnkey things
that help me evaluate agentic PRs quickly. You can often tell that they're
wrong almost instantly without reading any code, and then you give the agent
behavioral changes based on the video. There's just something about demos, and
video and voice together, that helps you reason extremely quickly. (It's
probably the same reason a live demo in a meeting usually goes better than
everyone reading the doc.)

This has really begun redefining how I write software outside of Stripe. In a
way it almost feels like scrolling TikTok. You're sending ideas at a bunch of
parallel coding agents and getting back full demo videos in minutes, over and
over.

## 3. Put every correction in AGENTS.md

When I correct an agent, I try to put the correction in `AGENTS.md` and not
just in the chat. If it's only in the chat it's gone the next session, and the
next agent makes the same mistake and I explain it again.

The `AGENTS.md` for this site has a paragraph that starts "Don't derive the
composition or the hue from the hash. It's the obvious move and it doesn't
work," and it's there because an agent made exactly that move and I didn't
want to have that conversation twice. After a while the file ends up being a
list of every mistake anyone has made in the codebase, written as
instructions, which is a pretty weird document but a useful one.

I try to write down why, too. If the agent only has the rule it'll follow it
in the situations I was picturing when I wrote it and then miss the next one.
It's the same thing I was getting at about [code explaining
itself](/blog/2026-10-29-software-archaeology), just for the agents.

## 4. Run the same prompt a few times

When something is ambiguous I've mostly stopped trying to write the perfect
prompt. I'll give roughly the same prompt to three or four agents in parallel
and then pick whichever one came out best.

Each attempt is basically free now, so the thing I'm actually short on is my
own time reviewing them. It's a lot faster for me to look at a few working
versions next to each other than to spec one out well enough that a single
attempt gets it right. And looking at them usually tells me what I wanted in
the first place, which I couldn't really have written down beforehand. A lot of
the time the answer is something like "the second one, but with the layout
from the third one," and that becomes the next prompt.

This goes really well with the walkthrough videos, since four PRs is a lot of
code to read but four short videos isn't.

## 5. Build one to throw away

Fred Brooks said to plan to throw one away, because you're going to anyways.
That's an old one, and I think it got a lot more useful.

If I don't really understand the problem yet, I'll have an agent build a fast,
sloppy version first, just enough to run. Then I look at it, figure out what
the thing should actually look like, delete the branch, and start over with a
much better prompt.

Actually deleting it is harder than it sounds. The sloppy version sort of
works, and it's really tempting to just keep going from there. But an agent
extending a prototype will happily build on top of every bad decision in it,
and pretty soon you've got layers nobody understands.

## More to come

I'm sure there are a lot more of these, and I'm still figuring a bunch of them
out. Probably most of them will seem obvious in ten years, the way the command
pattern seems obvious to me now that I know it has a name.
